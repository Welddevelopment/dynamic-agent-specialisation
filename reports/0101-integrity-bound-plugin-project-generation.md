# Checkpoint 0101 — integrity-bound plugin-project generation

Date: 2026-08-14  
Work item: DAS-025 / zero-spend productization lane  
Result: passed inside the frozen private deterministic local boundary

## Plain-English result

DAS could already turn reviewed business facts and pinned OpenAPI/MCP material into a complete, non-executable action/observer package. An engineer still had to decide how to lay out the actual plugin projects, separate the write path from the independent read-only proof path, declare every required interface, create the control skeletons and keep the generated bytes tied to the exact reviewed package.

DAS-025 now generates that complete fail-closed project shell automatically.

For each completed package, it creates two separate projects:

- an **action project** for the permission-bound write and action-plane reconciliation path; and
- an **observer project** for the separately authenticated, read-only external-outcome check.

Both compile as JavaScript projects, but every operational function deliberately throws. They contain no working transport, credential, authority grant or passing proof. The output tells the engineer exactly what remains to be implemented without allowing generated structure to masquerade as a working customer plugin.

## What is generated

Every generator invocation requires both the exact complete DAS-024 input draft and its matching DAS-023 generated package. A loose draft, a loose package or a cross-paired package is rejected.

The output includes:

1. one action-plane project and one observer-plane project;
2. provider-neutral plugin manifests bound to the exact draft, package, source family, source digest, transport, runtime schema, authentication identity and reviewed operation/tool identities;
3. environment-alias-only credential hooks with no credential values;
4. fail-closed interfaces for authentication inspection, action execution, action-plane reconciliation, durable action receipts, independent observation, an observer no-write probe, durable observations, evidence mapping and terminal classification;
5. all ten canonical outcome controls with exact expected classifications and dispositions, each labelled `declared-not-run`;
6. separate integrity controls;
7. private directory/file modes, an exact file allowlist, per-file hashes and one generated-project hash; and
8. a receipt that keeps execution, qualification and activation false.

The project manifests contain no scripts or dependencies. The inspector rejects extra files, changed files, path escape, symlinks, manifest scripts/dependencies, `eval`, dynamic imports, network fetch and secret-looking material.

## The critical identity correction

DAS-024 already had fields called `implementationHash`, but they were hashes of reviewed implementation labels—not hashes of source code. Treating those as code identities would let an intended design impersonate an implemented plugin.

DAS-025 separates four identities:

1. `implementationIntentHash` — what the reviewer said should be built;
2. `generatedProjectHash` — the exact generated scaffold bytes;
3. `implementationContentHash` — the exact separately supplied implementation bytes; and
4. `conformanceReceiptHash` — the exact implementation plus its qualification evidence.

The generated projects keep the last two fields null. Only the separate fictional implementation rehearsal creates content and conformance identities, and those identities do not modify or upgrade the scaffold.

## Separate fictional implementation and qualification

The generator did not secretly fill its own TODOs to make the experiment pass.

For both source families, a separate disposable implementation layer outside the generated project directories was bound to exact source-file byte hashes and an explicit fictional business-world profile. The DAS-023 package was then reissued against those actual action and observer content hashes.

That separately bound implementation entered the unchanged DAS-023 qualification runner. Each package passed the same ten controls:

- completed;
- not started;
- partial;
- incorrect;
- duplicate;
- stale;
- collateral;
- unknown;
- unavailable; and
- lost response.

The observer made zero writes. Both post-commit lost-response cases reattached to durable state and found the existing write without replay. The resulting conformance receipt binds the exact implementation bytes, qualification package, case contract, qualification receipt and local acceptance-only receipt.

This proves that the generated interface boundary is compatible with the existing qualification path. It does not prove that the generator authored a real customer connector.

## Adversarial coverage

The generator, inspector, focused tests and final rehearsal cover the preregistered failure classes:

- stale, mutated and cross-package drafts/packages;
- changed source, runtime schema, method/tool or generated release identity;
- shared action/observer source, transport, authentication identity or credential alias;
- secret-looking input or generated material;
- path escape, symlinks, unexpected files and overwrite;
- package scripts, arbitrary dependencies, dynamic execution and network fetch;
- missing or changed canonical controls;
- observer write surfaces;
- action-plane response/readback being confused with independent outcome proof;
- weakened retry, duplicate, collateral, unknown or unavailable semantics;
- generated-file or implementation-content substitution; and
- cross-role implementation replay.

The final campaign directly recorded 10/10 integrity-attack rejections. The broader focused chain passed 18/18 before sealing. The complete deterministic repository suite passed 475 tests, failed zero and skipped one localhost-permission case after the final source changes.

## Preserved v1 evidence issue

The first sealed campaign produced the same 20/20 control outcome and correctly detected source changes, but its source manifest labelled a canonical string-content digest as raw file SHA-256 while the implementation receipt used actual file-byte SHA-256. That was an evidence-labelling defect.

The v1 artifact remains preserved at `artifacts/onboarding/das025-plugin-project-rehearsal-v1/` and must not be cited as the final result. The v2 runner uses raw file-byte SHA-256 consistently; its source manifest remained unchanged during the fresh campaign.

## Exact remaining customer-specific burden

The generator retires repetitive project setup, not real customer truth or transport work. Seven concrete items remain:

1. implement the customer-local authenticated action transport and exact authority check;
2. implement action-plane readback/reconciliation before any retry;
3. map action evidence without calling it independent outcome proof;
4. implement the separately authenticated read-only observer transport;
5. map and classify fresh observer evidence, duplicates and collateral state;
6. resolve credential aliases inside the customer environment without persisting values; and
7. run conformance plus mandatory acceptance against the real customer test environment.

The two fictional packages still used 19 owner confirmations and 24 engineer confirmations each. Observer response schemas, request mappings, pagination/aggregation rules and proprietary authentication/transport behavior may add real work. The fact that the reusable disposable implementation needed zero package-specific executable files in these fixtures does not establish zero real-customer code or human effort.

After implementation, customer-environment acceptance, comparison readiness and controlled activation remain separate gates.

## Evidence boundary

The strongest accurate private statement is:

> From two complete fictional reviewed OpenAPI/MCP package receipts, DAS generated separate integrity-bound action and observer plugin projects with exact manifests, fail-closed interfaces and all ten canonical controls declared but unrun. Separately content-hashed disposable implementations then passed the unchanged twenty-control aggregate qualification path with zero observer writes or replayed lost-response writes.

This does not establish autonomous implementation of real customer plugins, arbitrary OpenAPI/MCP support, real credentials, customer execution, customer-environment acceptance, human setup-time reduction, comparison readiness, activation, production reliability, customer value or public evidence.
