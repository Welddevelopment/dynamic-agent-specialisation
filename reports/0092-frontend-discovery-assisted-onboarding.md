# 0092 — Frontend discovery joined to fail-closed assisted onboarding

## Verdict

The frontend-designer discovery result now enters the real assisted-onboarding product path instead of ending as an isolated contract preview. DAS can recognize the bounded frontend role, create an editable structured intake, persist it, and generate an exact private customer-binding scaffold.

The checkpoint deliberately stops before execution. The saved frontend revision is frozen as `design-and-scaffold-only`. It cannot accept a claimed binding descriptor, record binding acceptance, freeze a paid comparison plan, record a result or reach controlled activation until real customer-local design-source, repository/PR and independent repository-result bindings exist.

No model calls, external requests or paid spend were used for this checkpoint.

## What changed

- Added frontend implementation to the authoritative commercial role registry for discovery, structured intake and scaffold generation.
- Added a deterministic zero-cost frontend preview and a sanitized console label.
- Removed another duplicated three-role support list from the console projection path.
- Added explicit per-role lifecycle availability rather than treating `supported` as one overly broad boolean.
- Replaced ambiguous `provenBriefId` / `provenVerifierId` template metadata with local-fictional reference-evidence metadata that explicitly denies customer-binding evidence.
- Frozen lifecycle availability is stored inside each saved onboarding revision, so a later software update cannot silently promote an old intake.
- Every downstream frontend mutator fails before it can accept fabricated evidence: binding review, binding acceptance, comparison planning, result recording and controlled activation.
- A complete form no longer authorizes executable comparison. It can establish only that the comparison design information is complete.
- The console distinguishes `Design + scaffold supported · execution blocked` from a full assisted lifecycle and exposes the three concrete engineer-owned blockers.

## Skeptical technical-angel result

The checkpoint retires one material objection: a synthetic frontend world can no longer be mistaken for a customer-executable integration merely because frontend is now a recognized role.

The strongest surviving objection is still hidden setup work. A real frontend customer needs three substantive bindings, so DAS has not yet proved that a normal worker can reach the first tested specialist without engineer assistance. The next Lane A item should reduce and measure that binding work. The strongest Lane B objection remains the absence of a fair adaptive baseline showing that DAS autonomously produces a better specialist with less human agent engineering.
