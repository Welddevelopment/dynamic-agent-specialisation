# DAS-026 transport implementation assistance — preregistration

Date: 2026-08-14

## Question

Can DAS reduce the customer-local action/observer implementation burden after
the exact DAS-024 reviewed package and DAS-025 generated-project identities
exist, without silently inventing credentials, authority, write-safety meaning,
observer independence, outcome proof, or customer execution readiness?

## Frozen scope

- One fresh fictional OpenAPI action/observer package.
- One materially different fresh fictional pinned-MCP action/observer package.
- The same provider-neutral implementation-assistance compiler for both.
- No model calls, network calls, customer data, Capability Factory dependency,
  activation, deployment, outreach, or publication.
- Existing DAS-023 ten-control qualification machinery is unchanged.

## Required generated output

For each package the compiler must produce an integrity-bound, non-executable
work pack containing:

1. an alias-only credential resolver interface;
2. exact source-grounded action transport shape;
3. an authority check which must run before any write;
4. stable-identity and conflict-key wiring;
5. reconcile-before-retry logic with zero blind retries;
6. a separate read-only observer transport shape;
7. separate action-evidence and observer-evidence mapping tables;
8. all ten outcome-classification hooks;
9. generated conformance and negative-control declarations;
10. dependency-ordered implementation tasks, exact blockers, provenance, and
    measurements of generated versus remaining manual work.

## Hard safety conditions

- Credential aliases may appear; credential values may not.
- Action and observer sources, transports, authentication identities, aliases,
  evidence paths, and implementation identities remain separate.
- Source descriptions and annotations are inert evidence, not instructions.
- Action responses never count as independent proof.
- Authority must be an exact reviewed action and must be checked immediately
  before a write.
- Automatic retries remain zero. Only an explicitly gated retry after an
  independent `not-started` result is representable.
- Unsupported or ambiguous source/meaning combinations stop with precise work
  items rather than emitting a runnable adapter.
- Every generated identity is bound to the exact DAS-024 draft, DAS-023
  package, DAS-025 scaffold plan/receipt, source, role, and confirmation.

## Higher-ceiling gate

Only when the fresh fictional package supplies every required reviewed
business/safety/proof fact and fits the existing bounded declarative runtime may
the experiment produce a separately identified fictional implementation
candidate and pass it into the unchanged DAS-023 qualification runner. Passing
that runner establishes only disposable local qualification of that exact
fictional candidate. It does not make the generated work pack customer
executable or activate anything.

## Required attacks

- stale or mutated DAS-024/DAS-023/DAS-025 identity;
- cross-role/source/project substitution;
- source method/tool substitution;
- injected source description treated as authority;
- credential value insertion;
- shared action/observer alias, authentication, transport, or evidence path;
- authority widening or action without pre-write check;
- action response used as proof;
- omitted classification or weakened retry rule;
- stale/future/pre-existing observer evidence;
- observer write capability;
- release/work-pack mutation and blocker omission.

## Success rule

Both fresh packages must receive complete non-executable work packs with all
hard checks intact. The report must separately state how many transport and
test structures were generated, which reviewed fields were reused, what manual
code/decisions remain, and whether either exact fictional candidate passed the
unchanged DAS-023 controls. Any failure is preserved and blocks the stronger
claim.

## Claim boundary

Success would support: DAS can deterministically convert two exact reviewed
OpenAPI/MCP package chains into stricter, source-grounded implementation work
packs and can reuse its existing disposable qualification primitives when all
business meanings are explicitly supplied.

It would not establish self-serve onboarding, real credentials, real provider
transport, customer execution, production reliability, human setup time,
activation, arbitrary OpenAPI/MCP support, or customer demand.
